# R9700 Hub

AMD Radeon AI PRO R9700 소식·기술·가격·작품을 모으는 한국어 독립 사이트다. 공개 기준 주소는 **https://r9700.jjgo.io**이며 DNS는 아직 연결하지 않았다. Astra가 운영 엔진을, Luna가 공개 화면과 호스트 컨트롤러를, 부모 세션이 인증·통합·배포 구성·브라우저 검증을 구현했다.

```powershell
npm ci
python -m ops.r9700 init
npm run local
```

로컬 주소는 **http://127.0.0.1:4321**이다. `npm run local`은 웹과 6시간 운영 스케줄러를 함께 실행한다. 웹만 실행하려면 `npm run dev`, 한 번 수동 운영하려면 `python -m ops.r9700 run`을 사용한다. 관리자 설정은 `.env.example`과 `/admin`에서 확인한다.

## 화면과 탐색

상단 메뉴는 소식 / 가이드 / 가격의 세 개로 단순화하고 전체 검색을 제공한다. 소식에 뉴스·후기·외부 리뷰를, 가이드에 기술·설치·호환성·벤치마크·문제 해결·자료실을, 가격에 제품 비교·가격·재고를 묶는다. 기존 상세 자료는 독립 URL과 태그로 유지한다. 홈은 최신 소식 목록, 가격 요약, 시작 가이드와 작품 미리보기로 구성한다. 작품 미리보기에는 대표 이미지와 클릭해서 재생하는 영상 포스터를 소수만 배치하고 “R9700 작품 보기”로 독립 갤러리에 연결한다. 장식용 배너·복잡한 대시보드·강제 회원가입을 두지 않는다. 특정 제품·도구·오류 페이지에서 관련 자료를 연결한다.

콘텐츠 상세에는 원문 링크, 원저자, 원문 게시일, 갱신일, 수집일, 마지막 확인일, 관련 제품과 버전, 근거 상태를 표시한다. 날짜가 없는 자료는 날짜 미상으로 남긴다. 원문과 사이트 자체 해설의 작성자를 구분한다.

뉴스·후기·가이드·자료실은 공통 목록과 상세 템플릿을 재사용하고 가격·호환성·갤러리에만 별도 보기를 둔다. 갤러리는 홈뿐 아니라 검색·전체 자료 탐색·푸터에서도 항상 찾을 수 있게 한다. 독립적인 비공식 사이트임을 표시하고 출처·정정 및 삭제 요청·최소 개인정보 안내를 제공한다. 제휴 링크가 생기면 해당 링크에 표시한다.

한국어 및 영어 검색어를 지원한다. R9700, Radeon AI PRO R9700, Radeon PRO AI R9700, AI Pro 9700, 라데온 AI 프로 R9700 등 표기를 정규화한다. gfx1201·RDNA4·ROCm은 관련성이 확인된 글만 포함한다. ATI Radeon 9700 Pro와 Ryzen 7 9700X는 다른 제품으로 분리하고 R9700S는 별도 모델로 관리한다.

## 이미지 배치와 R9700 작품 갤러리

사이트 이미지는 정보를 이해하고 작품을 감상하는 데 필요한 위치에만 배치한다. 홈에는 실제 작품 미리보기, 가이드에는 개념 그림과 필요한 화면 예시, 리뷰에는 허용된 제품 이미지 또는 원저자 미디어, 작품 페이지에는 실제 결과물을 사용한다. 가격 화면은 그래프와 제품 식별 이미지에 집중한다. 글마다 같은 크기의 장식용 커버를 강제로 넣지 않는다.

이미지 생성 도구는 가이드의 개념 일러스트, 필요한 커버, 홍보용 배경을 만드는 데 사용한다. 실제 제품의 외형·포트·PCB·설치 화면을 생성 이미지로 대체하지 않는다. 사양 전달에는 공식 자료나 직접 촬영한 사진을, 수치 전달에는 실제 데이터로 그린 차트와 도식을 사용한다. 생성 배경 위의 제목·수치는 웹 또는 그래픽 편집으로 정확하게 배치한다. 사이트용 생성 이미지는 R9700 실행이 확인되지 않았다면 “AI 생성 일러스트”로 표시한다.

갤러리는 이미지·영상 탭과 모델·도구·단일/다중 GPU 필터만 제공한다. 이미지 카드에는 썸네일·작품명·모델·제작 근거 상태를 보여주며 클릭하면 확대와 상세 정보로 이동한다. 영상은 포스터·길이·재생 버튼을 표시하고 사용자 선택 시 재생한다. 모바일에서도 확대·전체 화면·재생·일시 정지가 가능하게 한다. 여러 영상을 동시에 자동 재생하거나 소리 나는 배경 영상을 사용하지 않는다.

작품마다 제작자, 결과물 파일 또는 허용된 원문 임베드, 모델 ID·버전, 도구·워크플로 버전, 해상도, 영상 길이·프레임 수, GPU 모델·수량, OS·ROCm·드라이버, 생성 시간, 게시 권한과 출처를 가능한 범위에서 기록한다. 자체 제작에는 실행 ID·완료 로그·GPU 식별·워크플로·시드·결과 파일 해시를 연결한다. 공개할 수 있는 프롬프트와 워크플로는 별도 보기 또는 다운로드로 제공한다. 영상 제작에서 생성·업스케일·보간·편집에 사용된 도구를 구분하고 생성 시간은 해당 단계와 측정 범위를 표시한다.

“R9700 직접 제작 확인”은 실제 실행 근거가 있는 자체 결과에, “제작자 R9700 사용 보고”는 제작자가 밝힌 외부 결과에 부여한다. GPU 근거가 없는 결과는 일반 참고 작품으로 분리하고 R9700 제작 필터에 포함하지 않는다. 대표 작품의 품질을 GPU 고유 성능으로 단정하지 않으며 관련 모델과 설정을 함께 보여준다. 참고 자료와 사이트용 일러스트를 R9700 제작 작품으로 표기하지 않는다.

초기 작품은 기존의 실제 R9700 결과물 또는 출처·게시 권한이 확인된 외부 작품으로 채운다. 실제 작품 감상 완료에는 이미지 최소 1개와 영상 최소 1개가 필요하다. 결과물이 없으면 UI 구현만 완료로 보고 실제 이미지·영상 제공은 BLOCKED로 남긴다. 외부 작품은 원작자 링크와 허용된 임베드를 우선 사용하고 원본을 임의 복제하지 않는다. 작품 제보는 URL·제작자·권한·근거를 받는 작은 폼으로 구현하고 접수량을 제한한다. 공개 파일 업로드나 제출된 워크플로·custom node 자동 실행은 제공하지 않는다. 출처·권한·제작 근거를 확인한 후 공개한다.

6시간 운영 작업은 새 작품 등록, 파일·임베드 상태, 포스터·썸네일·대체 텍스트·레이아웃 누락을 함께 점검하고 보완한다. 필요한 사이트용 이미지가 없으면 주제에 맞는 생성 요청을 만들고 설정된 이미지 도구와 비용 한도 안에서 생성·검토·게시한다. 이미 적절한 이미지가 있으면 재생성하지 않는다. 자동 생성 이미지의 잘림·가독성·왜곡과 실제 페이지 배치를 확인한다.

R9700 자체 이미지·영상 생성은 별도의 로컬 GPU 작업 큐를 운영 작업에 연결할 수 있게 한다. 모델 파일 해시·허용된 workflowId·출력 경로·장치 식별자·사용 시간·동시성·실행 시간 한도와 장치 사용권을 먼저 설정한다. GPU가 한가하다는 사실만으로 사용권을 인정하지 않는다. 장치 소유권과 기존 작업 부재를 확인할 수 없으면 DEFERRED로 남긴다. GPU 호스트가 사용권을 획득한 뒤 최대 한 건씩 실행하며 타 작업 종료·공용 ComfyUI 전역 취소·드라이버 재설정을 하지 않는다. 긴 생성은 비동기로 실행하고 jobId·attemptId·실행 로그·제작 장치·결과 해시를 대조해 갤러리에 한 번만 게시한다. 임시 파일은 디코딩·영상 길이·프레임·완료 근거 확인 후 확정하고 작업 완료 즉시 GPU를 반환한다. 재시작 후에도 완료 결과부터 대조해 중복 생성하지 않는다. 준비·다운로드·대기·실행·실패·완료 상태를 구분한다.

이미지는 용도별 크기로 변환하고 가로·세로 치수를 명시해 로딩 중 레이아웃 이동을 줄인다. 화면 아래의 이미지와 영상은 지연 로드하고 영상 본문은 재생 요청 전까지 받지 않는다. 자체 영상은 브라우저에서 재생 가능한 보기용 파일과 포스터를 제공하고 Range 요청·탐색 재생을 실제로 검증한다. 원본 다운로드는 게시자가 허용한 경우만 노출한다. 미디어 원본은 정적 빌드에 복사하지 않고 DB 밖의 한 저장소에 보관한다. 메타데이터·해시·권한은 같은 SQLite에 저장한다. 초기 보관 한도 50GiB·최소 여유 공간 10GiB는 배포 디스크에 맞춰 확정할 제안값이다. 한도 도달 시 새 생성·업로드를 중단하고 정리 후보만 기록한다. 생성뿐 아니라 저장·재생 전송 비용도 한도로 관리한다. 권리 철회는 원본·파생 파일·캐시·검색·공유 미리보기의 공개 제거까지 처리한다.

## 출처 등록과 자동 수집

출처 목록은 sources.json에 저장한다. 본문 뒤의 링크 목록과 동일한 73개 항목이다. 이 목록은 이번 조사에서 발견한 초기 수집 대상이며 인터넷 전체를 빠짐없이 열거했다는 의미는 아니다. 뉴스·제품·개발 도구·후기·가격의 주요 경로를 폭넓게 포함하며 새 원출처를 발견하면 등록한다.

상태 “확인”은 최초 웹 조사에서 검색 결과 또는 페이지로 자료를 확인한 항목이다. “검색 확인”은 검색 결과 기반, “자료 확인”은 관련 글이 발견된 커뮤니티, “접근 제한”은 접근 차단이 관측된 항목이다. “후보” 10개는 대상 자료 또는 구체적 경로를 추가 확인해야 한다. 어느 상태도 자동 수집 성공이나 사용 허가를 뜻하지 않는다. automationVerified는 전 항목 false다. 독립 검증에서 실제 응답을 확인한 RSS·Atom·API는 별도 필드에 기록하며, 지속 수집 전 과정과 권한이 검증된 연결만 자동 운영 대상으로 활성화한다.

자료 URL과 신규 발견 경로를 구분한다. 각 출처에 resourceKind·publisherKey·discoveryEndpoint·fetchEndpoint·adapter·accessMode·policyCheckedAt·verifiedAt·probeResult를 둔다. 개별 기사 재조회는 새 기사 발견이 아니고, API 설명 페이지는 상품 응답이 아니다. 같은 게시자의 여러 글을 독립 수집기로 세지 않는다. 새 도메인은 candidate로만 등록하고 기존 허용 정책과 수집 검증을 통과한 뒤 활성화한다. 언어·지역은 별도 필드이며 카테고리 이름으로 추정하지 않는다.

| 출처 | 확인된 실제 경로 | 독립 검증 수준 |
| --- | --- | --- |
| AMD Newsroom | https://newsroom.amd.com/rss.xml | RSS 29개 단발 파싱 |
| ROCm 블로그 | https://rocm.blogs.amd.com/blog/atom.xml | Atom 10개 단발 파싱 |
| TheRock | https://api.github.com/repos/ROCm/TheRock/releases?per_page=1 및 https://github.com/ROCm/TheRock/releases.atom | JSON 릴리스 형태 및 Atom 루트 단발 확인 |
| Hacker News | https://hacker-news.firebaseio.com/v0/newstories.json | ID 배열 단발 확인·개별 글 관련성 미검증 |
| 네이버 쇼핑 | https://openapi.naver.com/v1/search/shop.json | 공식 문서상 경로·인증 요구 확인·상품 요청 미실행 |

단발 HTTP 성공은 수집 운영 성공이 아니다. 발견·파싱·관련성·반복 수집·중복 방지·이용 조건을 따로 기록한다. 73개 모두의 현재 접근·권리·파서는 검증되지 않았고 가격 관측 연결은 아직 0건이다. 자세한 관측 근거는 Astra 보고서에 있다.

수집기는 출처별 어댑터로 구성한다. 공식 API 또는 RSS/Atom을 우선 확인하고, 제공되지 않으면 이용 조건에 맞는 HTML 변경 감시를 사용한다. 로그인·차단·유료 경로는 접근 조건이 확보되기 전까지 비활성화하고 수동 등록을 제공한다. 출처 목록에 사이트가 있다는 이유로 모든 글과 이미지를 복제하지 않는다.

| 유형 | 제안 수집 방식 | 운영 주기 |
| --- | --- | --- |
| 공식 뉴스·기술 블로그 | 확인된 피드/API 또는 목록 변경 감시 | 6시간 |
| 문서·제품 사양 | 본문 해시·버전·canonical URL 변경 감시 | 하루 |
| GitHub | 릴리스·이슈·토론 API 또는 확인된 Atom, 키워드 및 구성요소 선별 | 6시간 |
| 리뷰·미디어 | 피드 또는 새 기사 후보 발견, 원저자 확인 | 6시간 |
| 커뮤니티·영상 | 사용 가능한 공식 API, 게시물 URL 수동 등록 | 6시간·수동 출처는 등록 시 |
| 가격·재고 | 허용된 API/판매처 어댑터, SKU별 관측 | 6시간 |

새로운 소식의 자동 수집과 사이트 반영은 6시간 주기로 확정한다. 공식 뉴스·기술 블로그·GitHub·리뷰·미디어·자동 수집 가능한 커뮤니티와 영상·가격·재고를 같은 주기에 갱신하고 정적 사양·문서는 하루마다 변경을 확인한다. 출처별 접근 제한은 준수하되 확인하지 못한 출처를 업데이트 완료로 표시하지 않는다. GitHub의 모든 커밋을 뉴스로 게시하지 않고 R9700/AMD 지원에 영향을 주는 변경을 선별한다. 검색 API는 API 키·비용·쿼터를 확인한 뒤 연결하며 키 없이 작동하는 수동 출처 등록과 직접 URL 수집도 제공한다.

### 6시간 자동 업데이트

사이트 운영 서버의 스케줄러가 한국 시간 00:00·06:00·12:00·18:00에 실행한다. 브라우저를 열어두지 않아도 동작하며 최초 배포 시 초기 수집을 한 번 실행한다. 서버가 중단되어 실행을 놓쳤으면 복구 후 마지막 성공 체크포인트부터 한 번 보충 수집한다. 이 계획 단계에서는 실제 서버 작업을 등록하지 않는다.

매 실행에서 이전 체크포인트보다 새로운 게시물과 수정된 게시물을 찾는다. 게시일이 늦게 노출되거나 목록 순서가 바뀐 자료를 놓치지 않도록 최근 48시간을 겹쳐 확인하고 원문 URL·출처 ID·내용 해시로 중복을 제거한다. 출처가 날짜를 제공하지 않으면 출처별 커서와 이미 본 항목 ID를 사용한다. 수정된 내용은 기존 항목의 개정으로 기록한다.

48시간 겹침만으로 누락 방지를 보장하지 않는다. 게시일보다 최초 발견 ID를 기준으로 수용하고 updatedAt·ETag·Last-Modified·본문 해시와 기존 항목 재확인을 함께 사용한다. 피드가 저장 커서까지의 기간을 덮지 못하면 허용된 아카이브·목록에서 보충하고 불가능하면 coverageGap을 남긴다. 30분 안에 끝나지 않은 백필은 backlog로 이어가며 미완료 커서를 전진시키지 않는다. 오래된 글 발견을 새 출시 소식으로 홍보하지 않는다. 문서에는 /latest/ 링크 외에도 실제 버전·관측일·해시와 가능한 버전 고정 URL을 기록한다.

관련성·출처 URL·접근 및 게시 정책을 통과한 제목·링크·분류와 확인된 게시일 또는 날짜 미상 상태의 새 자료는 자동으로 목록에 반영한다. 한국어 요약은 원문의 사실·수치·조건을 확인하는 검증 단계를 통과한 경우에만 함께 게시한다. 요약에 실패하면 원문 제목과 링크로 게시하고 요약 대기 상태를 표시한다. 근거가 충돌하거나 성능·호환성에 대한 새로운 결론이 필요한 항목은 관리자 검토 대기로 두되 다른 소식의 갱신은 계속한다.

새 자료를 게시하면 홈·뉴스 목록·관련 상세 페이지·가격 그래프·검색 인덱스·RSS를 함께 갱신한다. 변경이 없으면 기존 콘텐츠를 유지하고 마지막 확인 시각만 갱신한다. 화면에는 최근 수집 시도, 마지막 정상 반영 시각, 다음 예정 시각을 구분해 표시한다. 일부 출처 실패를 전체 최신 상태로 표시하지 않는다.

출처별 실패는 다른 출처와 분리하고 각 실패 시도 후 5분·15분·45분 간격으로 추가 최대 세 번 재시도한다. 429 응답은 Retry-After와 출처 제한을 우선 적용한다. 정기 파이프라인 하나와 같은 컨트롤러의 영속 작업 표를 사용해 재시도 시각에 실패 출처만 깨운다. 재시도가 점검·개선·홍보를 다시 실행하지 않는다. 실행 ID·30초 heartbeat·프로세스 생존과 출처 락을 함께 확인해 중복 실행을 막는다. 락 만료만으로 살아 있는 작업을 밀어내지 않는다. 작업 로그에 신규·수정·중복·검토 대기·실패·미완료 수를 기록한다.

collectedCheckpoint와 publishedRevision을 분리한다. 콘텐츠 스냅샷·가격 표시 데이터·검색·RSS·사이트맵·미디어 참조를 같은 releaseId로 준비한 후 함께 전환한다. 수집 성공 후 발행이 실패하면 영속 후보를 다음 회차에서 이어 게시한다. 사이트 회귀 시 이전 공개 산출물과 포인터만 복구하고 정상 가격 관측·생성 작업·외부 홍보 발송 장부는 되돌리지 않는다. 자동 코드 개선에는 DB 스키마 변경을 허용하지 않는다. DB 재해 복구는 별도 절차이며 외부 발송 기록 대조 전까지 홍보 발송을 멈춘다.

### 같은 작업에서 사이트 점검과 개선 및 홍보

6시간마다 다음 흐름을 하나의 운영 작업으로 실행한다. 새 소식이 없어도 점검을 수행하고, 개선이나 홍보의 근거가 없으면 해당 단계를 건너뛴다.

| 순서 | 자동 작업 | 결과 |
| --- | --- | --- |
| 1 | 소식·후기·가격 수집과 검증 | 새 자료 게시, 수정 반영, 불확실한 자료 보류 |
| 2 | 사이트 상태 점검 | 깨진 링크, 빈 페이지, 검색 실패, 모바일 넘침, 이미지·영상 재생과 제작 큐 상태, 오류·속도 회귀 확인 |
| 3 | 개선 필요성 판별 | 장애와 실제 사용 문제를 우선하며 이미 해결된 문제는 제외 |
| 4 | 작은 개선 구현과 검증 | 근거가 명확한 개선 최대 한 건을 격리된 변경으로 구현·빌드·검증 |
| 5 | 사이트 반영과 확인 | 정상 결과를 배포하고 실제 페이지 확인, 회귀 시 직전 정상 버전으로 복구 |
| 6 | 홍보 후보 선택과 발행 | 가치 있는 새 소식·가이드·가격 변화에 대해 자체 채널과 설정된 외부 채널 반영 |
| 7 | 운영 기록 | 수집·개선·홍보 결과, 사용량, 다음 실행 시각 저장 |

사이트 점검은 매 실행에서 주요 페이지와 모바일 화면을 확인하고 나머지 링크는 분할 순회해 하루 안에 전체를 확인한다. 외부 링크의 일시적 오류나 429 응답은 즉시 삭제하지 않고 반복 실패 여부를 확인한다. 검색 결과가 없는 실제 검색어는 설치법·FAQ·관련 자료 보완 후보로 사용한다. 이용 통계가 없거나 표본이 적으면 관측 가능한 오류와 자료 부족부터 개선하며 클릭률 상승을 추정해 주장하지 않는다.

자동 개선 대상은 깨진 내부 링크·누락된 메타데이터·중복 콘텐츠·명백한 모바일 레이아웃 오류·접근성 오류·검색 및 필터 버그·근거가 있는 오래된 설명·관련 링크 보완·이미지 최적화다. 증거가 있는 소규모 코드 수정도 포함한다. 문제가 없는 화면을 매번 다시 디자인하거나 글을 분량만 늘리기 위해 재작성하지 않는다. 광고 문구나 호환성·성능의 새로운 주장은 출처 확인 없이 추가하지 않는다.

수정 프로세스에는 공개 템플릿·스타일·검색/필터 구현·근거 있는 설명의 허용 경로만 제공하고 운영 비밀·운영 DB·배포 권한을 주지 않는다. 인증·URL 방어·수집/가격/검증 정책·스케줄러·배포/복구·DB 스키마·의존성/잠금 파일·필수 검증기 변경은 자동 적용하지 않는다. 수정 AI가 필수 테스트를 삭제·완화할 수 없게 고정하고 재현 테스트 추가만 허용한다. 고정된 운영 컨트롤러가 검증된 산출물 해시와 기존 스키마 호환성을 확인해 전환한다. AI 실행 도구가 설정되지 않으면 자동 코드 수정은 BLOCKED로 기록하고 수집·점검은 계속한다.

자동 개선은 회차당 최대 한 건, 문제당 최대 두 시도, 최대 5개 파일·200개 변경 행으로 제한한다. 같은 실패를 새 근거 없이 반복하지 않는다. 개선의 실패 상태와 정상 콘텐츠 발행 상태를 따로 기록해 이미 게시한 뉴스와 가격까지 실패 처리하지 않는다.

변경 전 정상 소스와 발행 데이터를 보존하고 운영 중인 파일을 직접 덮어쓰지 않는다. 해당 문제의 재현 및 해결, 기존 주요 기능, 빌드, 모바일 화면을 확인한 뒤 새 버전을 전환한다. 배포 후 핵심 페이지·검색·가격을 다시 확인하고 실패하면 복구한다. 삭제가 필요한 자료는 개정 또는 비공개 상태로 남겨 복원할 수 있게 한다. 큰 구조 변경·대량 삭제·유료 서비스 가입·의존성 대규모 변경은 자동 적용 범위에 넣지 않고 개선 후보로 기록한다.

매 정기 실행의 작업 마감은 30분이다. 초기 전체 수집·백필과 GPU 생성은 이 마감과 별도로 관리한다. 수집/검증 8분, 콘텐츠 발행·필수 점검 5분, 개선 생성 7분, 개선 검증·전환 6분, 홍보·기록 2분, 복구 여유 2분을 초기 배분안으로 둔다. 시간이 부족하면 개선을 시작하지 않고 이어할 작업을 남긴다. 글로벌 동시 수집 4개·도메인별 1개·최소 간격 2초·요청 제한 20초·출처 시도당 120초·새 후보 최대 200개는 최초 성능 검증에서 조정할 제안값이다. 출처 제한이 더 엄격하면 그 조건을 우선한다.

AI·이미지·검색/가격·홍보 API의 유료 비용 한도가 null이면 호출을 비활성화하며 무제한으로 해석하지 않는다. 통화·일/월 한도·요청 최대치를 설정한 뒤 예상 최대 비용을 먼저 예약하고 실제 사용량과 정산한다. 사용량이 불명확하면 예약액을 유지하고 유료 작업을 멈춘다. 한도에 도달해도 일반 수집·가격 갱신·필수 점검은 계속한다. 호스팅·미디어 저장/전송·GPU 전력은 별도 비용으로 기록한다. 미설정 공급자와 예산은 최초 설정 묶음에 남긴다.

### 자동 홍보

기본 채널은 사이트 자체의 최신 소식·RSS·사이트맵·검색에 읽히는 상세 페이지·공유용 제목과 이미지다. 6시간마다 새 공개 자료의 설명·내부 연결·공유 메타데이터·사이트맵을 확인하고 누락을 수정한다. 검색엔진의 노출·색인 여부는 연결된 도구가 제공하는 근거만 표시하며 사이트맵 갱신을 노출 성공으로 간주하지 않는다.

외부 홍보는 하나의 운영자 소유 계정을 우선 연결해 단순하게 시작한다. 채널 후보는 X·Bluesky·Threads 등이며 최초 설정에서 대상 계정, API 자격 증명, 자동 발행 여부, 빈도와 문체를 정한다. 현재 채널은 미정이므로 계정 접근이나 게시를 실행하지 않는다. 연결 전에는 사이트 안의 발행 대기 목록에 문안과 링크를 저장하고, 자동 발행으로 설정된 채널은 매번 사람 확인 없이 발행한다. API·권한·이용 조건은 실제 연결 단계에서 확인한다.

매 실행에서 의미 있는 새 정보나 실용적인 기존 가이드, 게시 권한과 제작 근거가 있는 R9700 작품을 홍보 후보로 평가한다. 이미지 작품은 썸네일과 상세 링크를, 영상 작품은 포스터 또는 게시 가능한 짧은 미리보기와 상세 링크를 사용한다. 모델·GPU 수량·제작 조건을 사실대로 표시한다. 기본 발행 한도는 채널별 하루 한 건이며 중요 신규 정보가 없으면 발행하지 않는다. 한 번 홍보한 자료는 중복 발행하지 않고 실질적인 개정이 있으면 변경점을 포함한 새 후보로 관리한다. 반복 게시보다 “무엇이 바뀌었는가”, “누구에게 도움이 되는가”와 사이트의 해당 상세 페이지 링크를 짧게 전달한다. 가격 정보에는 관측 시각과 구매 조건을 붙인다.

발행 기록에는 콘텐츠 ID·개정 ID·채널·문안·사이트 URL·외부 게시 ID·발행 시각·추적 태그를 저장한다. 발행 결과가 불명확하면 기존 게시 여부를 확인하고 중복 전송을 막는다. 클릭·방문 지표가 제공되면 다음 후보의 주제 선택에 사용하되 소수 데이터로 홍보 효과를 단정하지 않는다. 커뮤니티 게시판의 무단 반복 게시·댓글·DM·대량 메시지와 유료 광고 집행은 기본 홍보에 포함하지 않는다.

홍보 유일 키는 channel·accountId·contentId·materialRevision으로 두고 문구만 바꾼 개정을 새 후보로 취급하지 않는다. DRAFT/READY/SENDING/SENT/UNKNOWN/FAILED/BLOCKED_AUTH 상태를 기록하며 응답 유실은 UNKNOWN으로 두고 원격 게시 대조 전 재발송하지 않는다. 계정별 KST 하루 1건에 최소 20시간 간격을 함께 적용한다. 발행 직전 대상 페이지 공개 상태·가격 최신성·작품 권한을 재확인한다. 게시와 대조에 필요한 계정 권한·비용을 실제 연결 시 확인한다. RSS·사이트맵 갱신은 외부 홍보 성공이나 방문 증가로 집계하지 않는다.

### 운영자가 보는 화면과 알림

관리 화면은 마지막 실행과 다음 실행, 활성 출처, 새 게시물 수, 최근 자동 개선, 홍보 결과, 비용·실패·보류 항목을 한 화면에 보여준다. 정상 실행과 변경 없음은 로그로만 남긴다. 사이트 반영 실패·자동 복구 실패·지속적인 수집 장애·계정 인증 만료·비용 한도 도달처럼 조치가 필요한 상태만 설정된 운영자 채널로 알리고 같은 장애를 반복 통지하지 않는다.

호스트 전체 중단은 해당 호스트가 스스로 통지할 수 없으므로 선택한 호스팅의 기존 외부 상태 확인 기능을 연결한다. 미연결이면 전체 호스트 장애 감지는 BLOCKED로 명시한다. 새로운 모니터링 플랫폼을 만들 필요는 없다.

## 무엇을 스스로 개선할 것인가

자율 운영의 단위는 “새 글 한 편”보다 “방문자가 풀지 못한 질문 한 개”로 둔다. 예를 들어 설치 가이드가 이미 있는데 검색되지 않는다면 새 가이드를 쓰기 전에 검색·별칭·연결을 고친다. 답 자체가 없으면 필요한 근거를 찾고 충분할 때만 해당 문단을 보완한다. 소식이 없는 회차에도 답을 찾는 경로와 근거 변경을 확인할 수 있다.

| 최초 구축에 채택할 아이디어 | 실행 방법 | 확인할 결과 |
| --- | --- | --- |
| 미해결 질문 장부 | 검색 무결과·반복 검색·간단한 피드백·고정 과제 실패를 OS·목적·증상별로 묶고 답 없음/발견 실패/조건 불명을 구분 | 같은 질문의 올바른 답 도달과 검색 결과·반례 확인 |
| 근거 변경에 따른 설명 보완 | 원문 개정과 가이드 문단·호환성 행을 연결하고 영향을 받는 부분만 갱신 | 근거 연결·적용 조건·실제 내용 변경, 단순 날짜 갱신 제외 |
| 한 변경의 전후 과제 검증 | 같은 데이터와 환경에서 변경 전후의 사용자 과제·기존 필수 검증을 비교 | 과제 성공 n/N·도달 단계·잘못된 제품/조건·성능 회귀 |
| 출처 가치와 비용 장부 | 고유 근거와 중복 사건을 구분하고 같은 원문의 파싱·요약을 재사용 | 필수 영역 누락 없이 고유 근거당 처리 시간·비용 감소 |
| 실패와 재개 조건 기록 | 시도·근거·실패 이유·재개 조건을 운영 DB에 남기고 다음 회차의 후보와 대조 | 같은 근거로 무효한 시도 반복 방지, 새로운 근거로만 재개 |

질문에는 signalOrigin을 기록해 실제 검색·제보·기술 재현과 초기 편집 질문을 구분한다. 초기에는 구매·설치·호환성·오류·작품 재현의 대표 질문을 editorial-seed로 등록하되 실제 사용자 수요로 표시하지 않는다. 행동 수집이 허용된 경우에만 짧은 방문 단위 중복 억제와 일별 집계를 사용하고 IP·전체 세션 녹화·사용자별 장기 이력은 요구하지 않는다. 원 검색어의 키·경로·계정처럼 보이는 문자열을 제거하고 길이를 제한한다. 이벤트 미수집은 실패 0건이 아니라 unavailable이다.

후보는 problemKey = 사용자 과제 + 적용 환경 + 실패 유형으로 묶고 대상·근거·변경·검증 방법이 갖춰져야 READY가 된다. 초기 반복 검색 신호는 7일 내 서로 다른 방문에서 같은 질문이 3회 이상인 경우로 제안한다. 이 신호만으로 기술적 답을 생성하지 않고 별도 내용 근거를 확보한다. 트래픽이 없는 초기에는 고정 과제의 재현 실패로 후보를 만들 수 있다.

자동 선택 순서는 ①현재 답을 망가뜨리는 장애·오류·확인된 잘못된 설명 ②답은 있는데 찾지 못하는 검색·링크·환경 필터 ③새 근거로 채울 수 있는 가이드·호환성·작품 설명 공백 ④중복 처리 비용·관측된 화면 불편이다. 같은 등급에서는 영향 범위·근거 강도·반복·대기 기간·작업량으로 정렬하고 불확실한 근거나 30분 안에 끝낼 수 없는 변경은 실행하지 않는다. 필요하면 Astra 제안의 정렬식과 예시를 참고하되 점수를 실제 사용자 효용 측정값으로 표시하지 않는다.

한 회차의 실질적 개선은 하나의 문제 묶음으로 제한한다. 하나를 해결하는 문단·링크·검색 갱신은 같은 묶음이고 별도 대형 편집 작업을 추가하지 않는다. 후보 선정과 교훈 확인은 기존 30분 안에서 60초 이내를 목표로 한다. 근거 없는 후보나 설정·예산 부족은 WAITING_EVIDENCE/BLOCKED_CONFIG로 남긴다. 후보가 없으면 NO_ACTION으로 정상 종료한다. 같은 문제 최대 두 시도 후 새 근거가 없으면 중단하고, 성공한 비긴급 변경에는 14일 재변경 유예를 둔다. 장애·확인된 오류·새 사실 정정은 예외다.

과제 묶음은 설치 경로·호환성 조건·가격 조건·작품 근거/재생을 포함한 12개를 초기 안으로 두고 별칭·표현 변형·다른 제품 반례를 함께 확인한다. 수정 AI가 기대 답·분모·필수 검증을 바꾸지 못하게 한다. 기술 해결, 근거 충족, 실제 방문 효과를 각각 기록한다. 전후 7일의 방문 효과는 같은 의도·환경·유입 조건으로 비교하고 각 기간 50개 미만이면 효과 미확인으로 남기는 초기 정책을 둔다. 50개 이상도 인과 효과를 보증하지 않는다. 14일에 관측을 종료하고 표본 부족을 이유로 화면을 계속 바꾸지 않는다.

출처 후처리 캐시 키에 원문/개정 해시·파서·프롬프트 버전을 포함한다. 6시간 수집 주기와 공식 지원·독립 실측·드문 지역 가격의 필수 감시는 유지한다. 낮은 인기도나 새 글 부재만으로 출처를 폐기하지 않는다. GitHub 저장소 등은 도메인뿐 아니라 저장소·게시자와 원문 계보까지 구분한다. 원문 페이지의 메뉴·푸터만 바뀌면 가이드 전체를 재작성하지 않는다.

뉴스와 작품이 새로 답하게 된 질문은 기존 가이드·작품 상세·홍보 후보에 함께 연결한다. 홍보는 “누구에게 / 무엇이 달라짐 / 확인할 안내 / 근거와 한계”를 짧게 전달한다. 작품 수를 늘리기 위한 GPU 생성보다 기존 결과의 제작 조건·관련 가이드·캡션 보완을 우선한다. 관리자에는 “지금 조치 / 이번에 나아진 점 / 관찰·보류 이유”를 고정 템플릿으로 보여주고 자세한 로그는 펼쳐 본다.

소식 없는 회차는 정상 수집과 변경 없음인지 먼저 확인한 뒤 고정 과제·기한이 된 근거·기존 작품의 연결을 점검한다. 할 일이 없으면 게시와 홍보를 만들지 않는다. 자동 방문자 A/B 플랫폼·가격 예측·복잡한 환경 자동 탐지·인기 없는 출처 폐기·정기 GPU 작품 양산은 기본 범위에 추가하지 않는다.

ROCm/ROCm은 조사 시 legacy-rocm-build로, 기존 Radeon ROCm 문서는 radeon-ryzen 문서로 리다이렉트되었다. 입력 URL과 최종 URL을 함께 저장해 출처 이동을 추적한다. 현재 ROCm 변화는 TheRock·rocm-systems·rocm-libraries까지 감시 대상으로 등록한다.

## 수집 후 게시 흐름

발견 → 원본 메타데이터 보존 → URL 정규화 → 중복 판별 → 관련성 분류 → 한국어 요약 초안 → 사실·조건 검토 → 게시 → 변경 및 삭제 확인.

추적 파라미터를 제거하되 상품 ID·페이지 ID 등 의미 있는 파라미터는 유지한다. 제목·canonical URL·원문 출처·내용 해시를 활용해 재게시와 동일 사건을 묶는다. 기사 수와 독립 근거 수는 별개다.

AI는 번역·요약·태그·연관 링크 후보를 작성할 수 있다. 가격·성능·호환성 수치는 원문에 근거가 있는 값만 기록한다. AI 연동이 없어도 수집·검색·원문 링크·수동 편집·게시가 동작해야 한다. 외부 본문은 처리할 데이터이며 실행 지시로 취급하지 않는다.

요약의 수치·지원 주장에 원문 위치·해시·제품·OS·버전·측정 조건을 연결하고 단위·부정문·지원 범위의 왜곡은 보류한다. 같은 모델의 재검토나 자신감 점수만으로 검증 상태를 부여하지 않는다. 외부 원문·AI 요약은 텍스트 또는 제한된 Markdown으로만 렌더링하고 MDX 코드로 컴파일하지 않는다. 자체 신뢰 문서에만 MDX를 허용한다. URL 등록·링크 검사·미디어 수집은 같은 검증 경로로 HTTP(S), DNS 결과, 매 redirect를 확인하고 loopback·사설망·link-local·메타데이터 주소 접근을 막는다. XML 외부 엔티티와 위험한 HTML·스크립트·이벤트를 거부하고 임베드는 허용된 제공자의 고정 템플릿으로 만든다.

신뢰 상태는 공식 문서 / 제조사 주장 / 원저자 측정 / 사용자 보고 / 사이트 직접 검증 / 미확인으로 구분한다. 사용자 보고가 공식 지원 상태를 덮어쓰지 않는다. 근거가 충돌하면 조건과 차이를 함께 노출한다. 해결 상태는 제보 / 재현 / 우회법 / 수정 확인으로 관리하고 이슈가 닫혔다는 이유만으로 수정 확인을 부여하지 않는다.

요약과 링크를 기본으로 게시하고 전체 기사·포럼 글·썸네일·벤치마크 이미지는 이용 권한을 확인한 경우에만 재게시한다. 원문 변경·삭제·정정과 사이트 해설의 변경 이력을 남긴다.

출처·미디어별 접근 및 재게시 허용 범위와 확인 날짜를 저장한다. 원문 장기 보관이 허용되지 않으면 허용된 최소 발췌·해시·메타데이터만 증거로 남긴다. 삭제·권리 철회 때 공개 원본·파생 파일·검색·캐시·공유 이미지를 제거하고 허용된 최소 감사 기록만 보존한다. 공개 커뮤니티라는 이유로 API 상업적 이용이나 자동 재게시가 허용됐다고 판단하지 않는다.

## 가격 데이터 규칙

상품 ID, 제조사, 모델, 리비전, 유통사, 판매처, 지역, 통화, 기본 가격, 배송비, 할인 조건, 재고, 관측 시각, 출처 URL을 기록한다. 동일 상품이 여러 가격비교 사이트에 실려 있어도 판매처 URL·상품 ID로 중복 여부를 확인한다.

일반 구매 가격, 현금 전용, 카드·쿠폰·회원 할인은 각각 관리한다. 신품·중고·리퍼·해외 구매와 단품·완제품·다중 카드 묶음을 구분한다. 해외 가격은 원 통화 값을 보존하고 원화 환산에는 환율 출처와 시점을 기록한다. 세금·배송비를 모르면 국내 실구매가와 동일 조건으로 비교하지 않는다.

관측 멱등 키는 offerId·collectionEventId다. 같은 요청 재처리는 같은 이벤트 ID로 한 행만 저장하고 다음 6시간 회차의 같은 가격은 새 관측으로 추가한다. observedAt·receivedAt·출처 시각을 구분한다. 오파싱 정정은 원행을 지우지 않고 정정/무효화 기록을 집계에 반영한다. 판매처 구성 변화로 생긴 최저가 변화를 특정 제품 가격 하락으로 단정하지 않는다. 최신 관측이 12시간을 넘으면 stale로 표시하고 가격 홍보·알림에서 제외한다. 검색 API의 가격은 배송·실재고·가격 이력을 보증하지 않으므로 확보한 필드와 관측 범위만 기록한다.

가격 차트는 확보된 관측 기간만 그린다. 7일·30일·90일·전체 버튼은 해당 데이터가 있을 때 제공하고 부족한 구간은 비활성화 또는 자료 부족으로 표시한다. 최초 구축 때 과거 이력이 없어도 기다리지 않고 공개할 수 있다. 수집 실패, 가격 미표시, 품절은 각각 다른 상태이며 가격 0원이 아니다. “역대 최저가”는 실제 관측 기간 내 최저가로 표기한다.

NowInStock·가격비교 사이트의 과거 기록은 재사용 조건과 관측 시간·상품 식별이 확인된 경우에만 별도 출처로 들여온다. 직접 관측 이력과 수입한 이력을 구분한다. 그래프의 자료 공백을 채워 가격 하락·상승을 만들어내지 않는다.

## 호환성과 성능 데이터 규칙

호환성은 OS·버전·드라이버·ROCm·Python·프레임워크·엔진·GPU 수의 조합별로 관리한다. 공식 지원 / 실행 보고 / 직접 확인 / 미확인 / 알려진 문제를 표시한다. AMD GPU 지원이라는 문구만으로 해당 버전의 R9700 실행을 보증하지 않는다.

벤치마크에는 모델 ID와 버전·양자화·컨텍스트·입출력 길이·배치·동시 요청·GPU 수·분할 방식·엔진 커밋·드라이버·CPU·RAM을 가능한 범위에서 저장한다. 입력 처리, 생성 속도, 첫 응답 시간, VRAM, 전력, 온도, 소음을 분리한다. 조건이 다른 수치를 단일 순위로 혼합하지 않는다. 외부 측정, 자체 측정, 제조사 수치를 구분한다. 실패·오류·미실행도 보존한다. 전력 실측 없이 전력 효율을 결론내리지 않는다.

단일 32GB와 다중 GPU의 총 메모리를 구분한다. 두 카드의 합계 용량을 하나의 공유 VRAM으로 설명하지 않는다. 실제 분할 가능 여부와 오버헤드는 도구와 조건별 자료로 연결한다.

## 기술 구조 제안

Astro + TypeScript를 사이트 기본으로, 대화형 검색·필터·차트는 필요한 최소 컴포넌트만 사용한다. 별도 프런트엔드 프레임워크는 실제 필요가 확인될 때 추가한다. 자체 가이드와 해설은 Markdown/MDX, 외부 자료는 데이터, 구조화 자료와 운영 이력은 SQLite로 관리한다. Python 운영 컨트롤러 하나가 수집·점검·개선·홍보 단계를 수행하며 웹 요청과 분리한다. 공개 본문·검색은 정적 산출물을 사용하고 관리자·작품 URL 제보·선택한 서버 구독 경로에는 서버 어댑터와 입력 검증·인증/접수 제한을 적용한다.

단일 서버 또는 컨테이너 배포를 기본안으로 두어 SQLite·수집기·관리자를 운영할 수 있게 한다. 배포 대상·도메인·외부 API 키는 구성값으로 분리한다. 특정 호스팅 계약이나 공개 배포는 이 계획에서 실행하지 않는다.

데이터의 중심은 sources, source_fetches, products, offers, price_observations, content_items, content_sources, compatibility_records, benchmark_runs, known_issues, revisions다. 같은 SQLite에 operation_runs, improvement_changes, promotion_posts로 실행·개선·홍보의 증거를 기록한다. 별도 서비스나 대규모 에이전트 체계를 만들지 않는다. 가격 이력은 append-only로 관리하고 집계는 별도 계산한다. 출처 JSON은 등록용 초기 자료이며 실행 DB와 구분한다.

자율 개선에는 questions 표 하나를 추가하고 나머지는 기존 표의 필드를 사용한다. content_sources에는 claimKey·문단 anchor·버전 조건·근거 해시를, improvement_changes에는 problemKey·가설·선정 이유·전후 revision·측정 분모·중단/재개 조건을 둔다. 행동 집계는 허용된 경우에만 작은 일별 자료로 저장한다. 최초 구축에서 설계하며 운영 AI가 DB 마이그레이션을 실행하지 않는다.

작품과 이미지에는 같은 DB의 media_assets, showcase_items, generation_jobs로 파일·권한·제작 근거와 생성 상태를 관리한다. 실제 파일은 한 미디어 저장소에 두고 운영 작업 하나가 완료 결과를 등록한다. 장시간 GPU 작업은 독립 프로세스로 실행해 수집·점검·홍보를 막지 않는다.

수집 작업은 시간 제한·속도 제한·재시도·중복 실행 방지·체크포인트를 갖춘다. 한 출처 실패가 다른 출처와 사이트 전체 갱신을 막지 않도록 출처별 상태를 기록한다. 마지막 정상 결과는 유지하되 오래됨을 표시한다. 관리자에는 마지막 성공·실패 원인·후보 개수·게시 상태를 보여준다. DB 백업과 실제 복원 절차를 포함한다.

백업은 SQLite 온라인 백업으로 만들고 미디어 manifest·고정 소스/잠금 파일·설정 복원 방법을 함께 보관한다. 정상 공개 버전 5개, 일별 백업 7일, 운영 회차 후 일관된 DB 백업을 초기 제안으로 둔다. 호스트 밖 백업 위치를 설정해야 디스크·서버 손실 복원을 인수할 수 있다. 코드 복구 120초, 전체 복원 60분, 관측 손실 최대 6시간은 시험할 목표이며 이미 달성한 수치가 아니다.

## 일괄 구현 순서

1. 출처 레지스트리, 제품 ID와 데이터 스키마를 확정하고 중복·다른 제품 분류 규칙을 구현한다.
2. 최초 데이터 수집을 실행해 공식 사양·제조사 제품·확인된 뉴스와 리뷰·관측 가격을 넣고 원문 링크를 검토한다.
3. 출처 어댑터·검토·게시·수정 이력과 관리자 화면을 구현한다. 자동 수집할 수 없는 출처는 이유와 수동 경로를 표시한다.
4. 모든 공개 메뉴·상세·검색·필터·가격 그래프·호환성 표·연관 자료 연결을 구현한다.
5. 초기 설명·구매 판단·설치 안내·FAQ를 출처 기반으로 작성한다. 확인되지 않은 실행법은 외부 참고 자료로 표시한다.
6. 6시간 운영 작업의 수집·점검·자동 개선·홍보를 연결하고 모바일·검색·수집 실패·중복·가격 조건·관리자 인증·백업 복원·빌드·배포 후 확인·자동 복구를 검증한다.
7. 최초 전체 버전을 완성하고 출처별 작동 여부·데이터 범위·배포 명령·필요 설정을 인수 자료에 기록한다.

## 완료 기준

기능 구현·외부 연결·실데이터·공개 배포를 각각 PASS/FAIL/BLOCKED/NOT_RUN으로 인수한다. 미설정 기능의 구현과 모의 검증도 같은 최초 전체 구축에서 완성하되 실제 외부 운영 성공으로 보고하지 않는다. 필수 영역이 비어 있거나 미연결이면 “전체 운영 완료” 판정을 보류한다. 배포 호스트·AI/이미지 도구와 예산·홍보 계정·GPU 사용권/워크플로·실제 작품·가격 공급자·알림/외부 상태 확인/백업 위치는 한 번의 최초 설정 묶음으로 관리한다. 주차별 출시나 매 회차 사람 승인으로 바꾸지 않는다.

검증 사례는 ASTRA_REVIEW.md의 A01–A18을 구현 인수 명세로 채택한다. 고정 테스트와 fixture는 자동 수정 범위 밖에 두고 공개 초기 자료와 섞지 않는다. 가상 시간의 스케줄 검증과 실제 24시간 4회 실행 증거를 구분한다. 주요 모바일 화면은 동일 브라우저·네트워크 조건의 전후 3회 중앙값으로 비교하고 영상은 재생 전 본문 요청이 없는지 확인한다.
